Creación de un serializer para el modelo principal con validaciones. Diseño de los serializers del proyecto Django REST personal.
1. Objetivo de la sesión

Al finalizar esta sesión, el aprendiz será capaz de crear un ModelSerializer, entender la diferencia entre serializar (modelo → JSON) y deserializar (JSON → datos validados de Python), y agregar validaciones personalizadas y campos calculados a un serializer.

2. ¿Qué es un Serializer?

La sesión pasada convertimos manualmente cada libro a un diccionario dentro de la vista. Eso funciona para un caso simple, pero se vuelve repetitivo y frágil: si mañana agregamos un campo al modelo, tendríamos que recordar añadirlo también en cada vista donde armamos el diccionario a mano.

Un Serializer centraliza esa traducción en una sola clase, de forma parecida a como un ModelForm centraliza la validación de un formulario HTML. DRF ofrece dos formas principales:

ClaseUso
serializers.SerializerSe definen los campos a mano, uno por uno. Útil cuando los datos no vienen directamente de un modelo.
serializers.ModelSerializerGenera automáticamente los campos a partir de un modelo, igual que ModelForm lo hace con formularios. Es la opción que usaremos casi siempre.
💡 Idea clave
Un serializer hace dos trabajos, no solo uno: (1) convierte objetos Python a JSON para las respuestas (serialización), y (2) toma JSON entrante, lo valida y lo convierte en datos limpios de Python listos para guardar (deserialización). Es el equivalente DRF de un ModelForm.
3. Creación de un ModelSerializer

Crea el archivo biblioteca/serializers.py:

from rest_framework import serializers
from .models import Autor, Libro

class AutorSerializer(serializers.ModelSerializer):
    class Meta:
        model = Autor
        fields = ['id', 'nombre', 'nacionalidad']

class LibroSerializer(serializers.ModelSerializer):
    autor_nombre = serializers.CharField(source='autor.nombre', read_only=True)

    class Meta:
        model = Libro
        fields = ['id', 'titulo', 'autor', 'autor_nombre', 'precio', 'disponible', 'fecha_publicacion']

fields puede ser una lista explícita (recomendado, evita exponer campos sin darte cuenta) o el valor especial '__all__' para incluir todos los campos del modelo. autor_nombre es un campo calculado de solo lectura: usa source para navegar la relación y traer el nombre del autor sin que el cliente de la API tenga que hacer una segunda consulta.

Usando el serializer desde el shell (repaso de la sesión 2, ahora aplicado a DRF):

python manage.py shell
>>> from biblioteca.models import Libro
>>> from biblioteca.serializers import LibroSerializer
>>> libro = Libro.objects.first()
>>> serializer = LibroSerializer(libro)
>>> serializer.data
{'id': 1, 'titulo': 'Cien años de soledad', 'autor': 1, 'autor_nombre': 'Gabriel García Márquez', 'precio': '68000.00', 'disponible': True, 'fecha_publicacion': None}
4. Validaciones personalizadas

Además de las validaciones automáticas que DRF deriva del modelo (tipo de dato, longitud máxima, campos obligatorios), podemos agregar reglas propias de negocio con métodos validate_<campo> o validate:

class LibroSerializer(serializers.ModelSerializer):
    autor_nombre = serializers.CharField(source='autor.nombre', read_only=True)

    class Meta:
        model = Libro
        fields = ['id', 'titulo', 'autor', 'autor_nombre', 'precio', 'disponible', 'fecha_publicacion']

    def validate_precio(self, value):
        if value <= 0:
            raise serializers.ValidationError("El precio debe ser mayor que cero.")
        return value

    def validate(self, data):
        # Validación que involucra más de un campo a la vez
        if not data.get('disponible', True) and data.get('precio', 0) == 0:
            raise serializers.ValidationError("Un libro no disponible no puede tener precio 0.")
        return data

validate_<campo> valida un campo individual; validate (sin sufijo) recibe el diccionario completo y sirve para reglas que cruzan varios campos.

Deserialización y guardado de datos entrantes (simulando lo que hará una vista al recibir un POST):

>>> datos_nuevos = {"titulo": "Rayuela", "autor": 1, "precio": 45000, "disponible": True}
>>> serializer = LibroSerializer(data=datos_nuevos)
>>> serializer.is_valid()
True
>>> serializer.save()
<Libro: Rayuela>
⚠ Error común
Llamar a serializer.save() sin haber llamado antes a serializer.is_valid() lanza una excepción. Siempre hay que validar primero; en las vistas de la sesión 9 y 10 usaremos is_valid(raise_exception=True) para que DRF devuelva automáticamente un error 400 con el detalle.
5. Ejercicio práctico (para hacer en clase)
  1. Crea el archivo serializers.py en tu app principal y define un ModelSerializer para tu modelo más importante, listando explícitamente los campos que debe exponer.
  2. Agrega al menos un campo calculado de solo lectura usando source (por ejemplo, el nombre de una relación en lugar de solo su ID).
  3. Agrega una validación con validate_<campo> que rechace un valor inválido según la lógica de tu proyecto (por ejemplo, un precio o cantidad negativa).
  4. Agrega una validación con validate que dependa de al menos dos campos a la vez.
  5. Desde python manage.py shell, serializa un objeto existente e imprime serializer.data.
  6. Desde el shell, intenta deserializar un diccionario con un dato inválido y verifica que is_valid() devuelva False y que serializer.errors muestre un mensaje claro.
  7. Deserializa y guarda un diccionario con datos válidos usando serializer.save() y confirma en el Admin que el nuevo registro aparece.
6. Errores comunes
✗Usar '__all__' en fields sin pensarlo y exponer campos internos que no deberían salir en la API.
✗Definir un campo calculado sin read_only=True cuando en realidad no existe como columna en el modelo → error al intentar guardar.
✗Escribir la validación dentro del modelo o de la vista en lugar del serializer → la regla de negocio queda dispersa y es más difícil de mantener.
✗Llamar .save() antes de comprobar .is_valid() → excepción en tiempo de ejecución.
